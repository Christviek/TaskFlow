# Agile Team Charter — TaskFlow

**Student:** Christvie Kabangu  
**Project:** TaskFlow — Task Management Web Application  
**Date:** 27 October 2026  
**Methodology:** Agile  
**Project Status:** Functional application; core functionality manually tested.

## 1. Purpose

The purpose of this Agile Team Charter is to establish the purpose, goals, scope, working agreements, tools, and development approach for TaskFlow. It provides a clear framework for organising the work, managing priorities, tracking progress, and evaluating the outcome of the project.

Although the project is completed individually, Agile principles can still be applied to organise development into manageable tasks, review progress regularly, and make improvements based on testing and reflection.

## 2. Project Vision

TaskFlow aims to provide a simple and accessible web application that allows users to manage their personal tasks in one place. Users can create accounts, sign in securely, and create, view, update, and delete their own tasks.

The vision is to build a practical application that demonstrates full-stack web development, database integration, user authentication, and the application of Agile project-management principles.

## 3. Project Objectives

The main objectives are to:

- Develop a functional task-management web application.
- Implement user registration, login, and logout.
- Store user accounts and tasks persistently in a database.
- Ensure that users can access and manage their own tasks.
- Implement task creation, editing, viewing, and deletion.
- Provide a clear interface for managing and filtering tasks.
- Apply Agile principles to organise development and track progress.
- Document development evidence and reflect on the learning gained.

## 4. Project Scope

### 4.1 In scope

The project includes:

- Front-end development using HTML, CSS, and JavaScript.
- Back-end development using Node.js and Express.
- SQLite database integration for persistent storage.
- User registration and authentication.
- Password hashing and session-based authentication.
- User-specific task management.
- Task creation, viewing, editing, and deletion.
- Task filtering and dashboard statistics.
- Manual functional testing.
- Documentation of project planning, implementation, and reflection.

### 4.2 Out of scope

The following are not part of the current project requirements:

- A native Android or iOS application.
- Team collaboration and shared task lists.
- Third-party authentication, such as signing in with Google.
- Commercial deployment and ongoing public-user support.
- Advanced reporting and analytics.

## 6. Core Values

The project is guided by the following values:

- **Focus:** Prioritise features that contribute directly to the project objectives.
- **Adaptability:** Adjust the implementation when requirements or technical challenges require a change.
- **Quality:** Test functionality and correct identified problems.
- **Accountability:** Take responsibility for development decisions and deliverables.
- **Continuous improvement:** Reflect on completed work and identify opportunities to improve.
- **Transparency:** Maintain clear records of tasks, progress, decisions, and outstanding work.

## 7. Working Agreements

The following agreements guide how I manage the project:

1. Break larger features into smaller, manageable development tasks.
2. Prioritise work according to functionality, dependencies, and project objectives.
3. Keep the project files and documentation organised.
4. Test completed features before considering them finished.
5. Record important technical decisions and problems encountered.
6. Review progress regularly and adjust priorities when necessary.
7. Avoid adding features that do not support the project's current objectives.
8. Maintain accurate evidence and distinguish completed work from planned work.

## 8. Communication and Progress Tracking

Because TaskFlow is an individual project, communication mainly involves recording development decisions, tracking tasks, and reviewing progress.

The workflow follows these stages:

1. **To Do:** Work that has been identified but not started.
2. **In Progress:** Work currently being implemented.
3. **Testing/Review:** Work being checked against its requirements.
4. **Done:** Work completed and verified against its acceptance criteria.

## 10. Risks and Mitigation

| Risk | Mitigation |
|---|---|
| Technical errors during implementation | Test individual features, inspect error messages, and resolve issues systematically. |
| Loss of project files | Maintain appropriate backups and use version control where available. |
| Unclear or expanding requirements | Keep the project scope defined and prioritise essential features. |
| Authentication or access-control problems | Test registration, login, logout, and whether users can access only their own tasks. |
| Insufficient assessment evidence | Capture genuine screenshots and maintain the required Agile documentation. |
| Poor time management | Break work into smaller tasks and review progress against priorities. |

## 11. Definition of Done

A task is considered complete when:

- The required functionality has been implemented.
- The feature behaves according to its requirements.
- Relevant errors have been investigated and resolved.
- Appropriate functional checks have been performed.
- The implementation does not knowingly break existing functionality.
- Supporting documentation or evidence has been updated where required.

## 13. Reflection

Developing TaskFlow has helped me understand that software development involves more than writing code. The work also requires planning, defining requirements, organising tasks, testing functionality, and keeping track of decisions.

Breaking the project into smaller features made the development process easier to manage. For example, authentication, database integration, and task management each required attention to different parts of the application. Considering these features separately helped me approach the implementation in a more structured way.

The project also demonstrated the importance of defining the scope. Focusing on the core task-management functions helped me build a functional application before considering additional features. Testing the application allowed me to check whether its main functions behaved as expected.

One area for improvement is maintaining more consistent development records. A more detailed backlog and logbook would make it easier to trace how requirements changed, why certain decisions were made, and how much work each feature required.

Overall, TaskFlow has given me practical experience in organising a software project and applying Agile principles to individual development. I can use these lessons in future projects by documenting decisions earlier, reviewing progress more consistently, and linking completed work to clear acceptance criteria.

Together, these artefacts can demonstrate not only the application's development but also the planning, decision-making, and reflection involved in the process.
